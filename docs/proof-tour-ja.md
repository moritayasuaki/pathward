# PathWardの証明を読むツアー

最新の全定理・補助補題・各定理の使用公理・前提を含む型は
[証明台帳](../proofs/registry.json)で管理します。未証明の目標、優先順位、完了条件と
公理削減方針は[ロードマップ](../proofs/roadmap.json)にあります。
`make proof-check` は実際のRustからの再抽出、Leanの検査、公理監査に加え、
この台帳が古くなっていないことも確認します。更新はLeanのビルド後に
`python3 scripts/audit.py --write-registry` で行います。

今回の台帳は **613件の名前付き定理・補助補題**を含みます。98件は公理依存がなく、
`propext` を使うものは515件、`Classical.choice` と `Quot.sound` は各411件です。
属性 `@[simp]` 付きの補助定理3件も検出・監査するよう台帳生成を修正しました。
この件数は重複します。「613種類のサーバー全体の保証」という意味ではありません。
接続に関する18件と管理者切替に関する20件に続き、再起動・保存途中の復旧に関する28件を追加しました。
遷移モデルだけの定理は台帳の `scope: transition_model` で区別します。

これらはLeanの標準公理で、独自のセキュリティ上の仮定を公理として追加してはいません。
`Classical.choice` は存在する対象の非構成的な選択、`propext` は命題の外延性、
`Quot.sound` は商型の等式に関する公理です。後者は関数外延性経由でも現れます。
まず有限・決定可能な判断から不要な `Classical.choice` 依存の削減を検討します。
残り二つの全面除去は、LeanやAeneasのライブラリの構成にも関わるため、別の検討項目です。
公理を削っても、OS・TLS実装・実行器・抽出ツールの正しさが証明されたことにはなりません。

Leanで検証しているのは「すべてのサーバー動作」ではなく、実際のRustから抽出した
公開・制限・設定切替の判断です。試験が具体例を動かすのに対し、以下の定理は、
書かれた前提を満たす入力すべてについて成り立ちます。前提も保証の一部です。

## 1. 公開ルールを削っても、別のファイルが公開されない

旧設定に `/logo.svg → logo.svg` と `/manual.pdf → manual.pdf` があり、新設定から
後者だけを削るとします。新設定で許可される要求は、旧設定でも**同じファイル・同じ
GET/HEADの扱いで**許可されていた要求に限られます。削除が偶然別の許可を生むことはありません。

新しい `SafetyProofs.lookup_subset` と `authorization_subset` は、両方のルール表が
コンパイル検証に成功し、新表の宣言が旧表の部分集合であることを前提に証明します。
ファイル内容や公開ルートを変更した場合まで「同じ内容」とは言っていません。

## 2. 削除したURLは、クエリを足しても復活しない

`GET /manual.pdf?download=1` のパスは `/manual.pdf` です。
そのパスの宣言が新しい検証済みルール表に存在しなければ、静的配信の許可証は出ません。
`revoked_lookup` と `revoked_authorization` がこれを保証します。

これは新しい設定を参照する要求についての保証です。切替前に許可済みの要求は、
既に保持している旧設定とファイル記述子で完了できます。また、明示した別の
プロキシ規則で同じURLを転送するかは別の判断です。静的許可の削除だけで
すべての種類のルーティングを禁止する、とは主張していません。

## 3. 同じ古い設定からの二重更新を防ぐ

二人がともに世代7を見て設定変更を準備したとします。
最初の変更が成功して世代8になった後、もう一人が「世代7のはず」と送った変更は、
そのまま世代8を上書きできません。

`stale_after_success` は、成功した一回目の判断の直後に、同じ期待世代番号で行った
二回目の判断が現在の世代を保持することを証明します。世代番号が上限に達した場合も
既存の定理により巻き戻らず拒否されます。実装側はロック下でこの判断と切替を行います。
ロックや永続化そのものは、この定理だけでは証明されません。

## 4. 0-RTTは「少し早く届いたから許可」を増やさない

ハンドシェイク完了前には、公開済み静的ファイルへの匿名・本文なしGET/HEADだけを
通します。POST、プロキシへのGET、Cookie/Authorization付き、クエリ付きは対象外です。

既存の `DeliveryProofs.early_only_published_reads` は、早期許可からこの条件を導きます。
新しい `SafetyProofs.early_restriction` は、公開を取り消す、読み取り専用の条件を外す、
本文を増やす、機密情報ありと判定する、といった**条件の厳格化が拒否を許可に変えない**
ことを証明します。

HTTPの425応答と上流へ到達しない配線はRustの統合試験でも確認します。
TLS/QUICの暗号や「どんなネットワークでもPOSTが絶対一度だけ実行される」ことを
Leanで証明したわけではありません。許可した匿名静的GETは繰り返されても安全な
内容である必要があります。

## 5. 小分けに送っても、受信上限を抜けない

たとえば受信上限32KiBで、16KiB、12KiB、8KiBの順に届いた場合、最初の二つで28KiB。
最後の8KiBは合計36KiBになるので、解析器へ渡す前に拒否します。

`wire_run_accounting` は、**任意の有限個数**の受信片について、最終カウンターが
「最初の値＋許可した受信片すべての合計」に一致することを証明します。
`wire_run_bounded` は、その合計が上限以下で、64bit整数の範囲も超えないことを証明します。

前提は、各片を実際のRustの `wire_fits` で判定し、許可時だけそのサイズを足すことです。
実装の解析前アダプターがこの順序を使います。HTTP/3のフレーム分割やパケットの
届き方を変えても、正しく数えている限り、分割の数で上限は増えません。
OS・TLS・ライブラリ内部の全メモリがこの値に収まる、という証明ではありません。

## 6. 制限を厳しくしても、空き枠や残り時間が生まれない

同時処理上限を32から16へ下げ、20件がまだ処理中なら、新規の許可は出ません。
既存20件を即座に消したり、設定の世代が変わっただけでカウンターをゼロにしたりしません。
`service_tightening` は、同じ使用数で新しい上限を満たす要求なら古い上限も満たす、
つまり上限を下げて許可集合が増えないことを証明します。

`deadline_tightening` も同様に、同じ経過時間で期限を短くしても、期限切れが生存へ
変わらないことを保証します。時計やカウンターをリセットしない配線は実装の責務です。
QUICの移動後も元のIPへ課金し続けることはRustの所有権設計・実通信試験で確認しており、
QUICの移動プロトコル全体をLeanで証明したという意味ではありません。

## どこまで信用してよいか

| 区分 | 今回の扱い |
| --- | --- |
| Rustの純粋な判断と、その判断を組み合わせた上記の性質 | 実コードをCharon/Aeneasで抽出し、Leanで証明 |
| 手書き説明と抽出モデルのずれ | `make proof-check` で再抽出結果を比較 |
| 証明の穴・追加の公理 | 613件の定理・補助補題を監査。標準の `propext`、`Classical.choice`、`Quot.sound` だけ |
| パーサー、実際の通信、ロック、ファイル操作、秘密鍵保存 | ソースレビュー・境界試験・Linux統合試験 |
| rustls/Quinn/h2/h3/圧縮ライブラリ、Rust/Leanツールチェーン、OS | 信頼する土台。依存固定・監査・実通信試験で補う |
| 公衆回線、公開CA、実運用の全負荷 | 別の移行試験。ローカル試験だけでは完了扱いにしない |

追加した10件は [SafetyProofs.lean](../proofs/SafetyProofs.lean) にまとめています。
613という数には補助定理も含みます。重要なのは件数より、具体的な攻撃・操作と
保証、そして前提を対応づけられることです。

## 7. キャンセル済みの要求で待機枠を塞がない

HTTP/2の一斉再読込で、キャンセル済み要求が受付待ちに残る問題を再現しました。
修正では、キャンセルを先に確認し、待っていたFutureを破棄して枠を解放します。
全体の待機枠が満杯でも、接続ごとに最大1件のヘッダーを保持してキャンセルを消化します。
この保留ヘッダーも「接続内32件」の枠に含めます。

実際のRustから抽出した判断について、キャンセルを確認した場合は常に破棄し、
5秒以上経過した保留から新たな受付を始めないことを証明しました。
さらに、受付・保留から処理への移動・破棄・完了という状態遷移モデルでは、
**どの順序で何回進んでも「処理中＋保留中」が32以下**であることを証明しました。
保留から処理へ移す際に、保留枠を残したまま処理枠を増やしてはいけないことも明確になります。

この状態モデルとasync実装全体の対応、Atomicの会計、RustのDrop、実行器の公平性は
まだ形式証明の範囲外です。「必ず何ミリ秒以内に解放する」「送信済みの更新も取り消す」
とは主張していません。これらの区別と追加目標は台帳で継続管理します。

## 接続の入れ替えと停止を分ける

HTTP/2では、新しい要求の受付を止めても、既に受け付けた応答は残ります。
普通の接続入れ替えで、その応答を一律5秒で切るのは誤りでした。また、最後の
DATAフレームをライブラリへ渡した時点と、ネットワークへ送信した時点も異なります。

`CancellationProofs.retirement_preserves_active` と `retirement_preserves_held`
は、実行中・保留中の要求がある通常の入れ替えで、終了ゲートが閉じる判断を
返さないことを証明します。`shutdown_deadline_closes` は明示的な停止の5秒上限を
別に扱います。応答ごとの期限と全体の上限は残っています。

実際のTLS試験では、GOAWAY後も6.5秒待つバックエンド応答の本文まで確認します。
これらは終了判断と回帰試験の保証であり、ネットワーク到達やOSの時計の正しさを
Leanで証明したという意味ではありません。

## HEADと応答メモリの追加保証

HEADは「本文を送らず、ヘッダーだけ返す」要求です。上流が誤って本文や別のHTTP応答まで送っても、
Rustの本文選択は必ず破棄になります。実装では、その上流接続を使い回さず閉じます。
`ProxyProofs.head_discards_prefix` が選択部分を証明し、偽の応答を混ぜた通信試験で実装を確認しています。

小さい画像にも大容量ファイル用の最大枠を予約すると、同時利用できる人数が減ってしまいます。
今は応答の長さを検証してから本文領域を予約します。長さが不明なら設定上限を使います。
`DeliveryProofs.response_storage_covers_copies` は「本文2個分＋256 KiBが予約に収まる」ことを保証します。
予約が確保できる前には本文を確保しません。OSやアロケータを含む全メモリ使用量の証明ではありません。

ホスティング側の公開更新は、私有スナップショット→Rust設定検証→世代付き切替→受領票の順です。
古い受領票・古い期待世代・外向きリンクの拒否と切り戻しはLinux統合試験で確認しています。
公開更新の受領票の条件と状態モデルは `PUBLISH-RECEIPT` で証明済みです。Rustの実ファイル操作・設定観測とモデルの全対応は残しています。
管理者プロセス障害のガード保存に加え、再起動時の選択と部分書込みのモデルを証明しました。
同一計画のガード更新判断と中断モデルも `RECOVERY-UPGRADE` で証明済みです。
Python/systemd・実ディスク操作との全対応は `DEPLOY-CRASH` に残しています。
同じサービス役割の計画変更は `GUARD-PLAN-MIGRATION` で証明済みです。
役割やunit契約が異なる移行の判断・中断モデルも `GUARD-ROLE-MIGRATION` で証明済みです。任意のsystemd契約への一般化と実装全体の対応は残しています。


接続終了にも、別々の時計が必要です。「最後の処理から5秒たった」ことと
「終了予告を始めてから5秒たった」ことは同じではありません。
`retirement_grace_starts_at_retirement` は、通常の強制終了で後者の猶予を
前者の待ち時間で代用できないことを証明します。実TLS試験では、旧実装が
終了予告を送る前に切断することと、修正後にGOAWAYが届くことを確認しました。

## 処理終了と送信完了を分ける

画像を送り終えるには、アプリが本文を用意するだけでなく、HTTP/2とTLSの
送信待ちも空になる必要があります。`h2_pending_blocks_normal_close` は、
その送信待ちがある間は通常終了を許可しないことを証明します。
明示的な停止の5秒期限は別に保ちます。最後の処理が終わってから30秒たっても
送信待ちが残る場合は、成功とせずタイムアウトにします。残りの定理は
この期限の前後と、実行中・保留中の処理を誤って終わらせない条件を扱います。

これは7件の定理・補助補題を追加した判断部分の保証です。実際の送信待ちの
観測は信頼境界として残り、8秒間の書き込み停止とフラッシュ停止を別々の
回帰試験で確認します。ネットワーク全体の無故障を証明したものではありません。


## 相手が受信する前に接続を壊さない

TLSの送信待ちが空になっても、本文が相手に届いたとは限りません。LinuxのTCP送信領域に
残っている間に接続を破棄し、遅れてきたPINGと競合すると、画像が途中で切れることを再現しました。
修正では送信側だけを閉じ、相手の終了を待ちながら残りの受信を捨てます。この間はHTTP要求を実行しません。

`h2_peer_drain_bounded` は、その待機を許すRust判断が**30秒未満かつ受信1MiB未満**に限られると証明します。
時間または容量の上限に達したら許可しないことも別の定理です。到着するデータで時計を延長しません。
TCPの到達保証、OSの半閉鎖、非同期アダプター全体は、この証明の前提であり通信試験で確認します。


## 非同期接続：別の候補を試しても期限を延ばさない

CAへ接続するとき、最初のIPv6が応答しなくても別のIPv4を試せます。
ただし、各試行で30秒を取り直すと、総待ち時間が増え続けます。
今はDNS開始前の時計を最後まで共有し、最大8候補、全体の予算は30秒以下です。

`ConnectionProofs.launch_bounded` と `ninth_attempt_denied` は、実Rustの開始判断で
9回目を許さないことを証明します。`deadline_wins_over_success` は、期限に達した時点で
成功を受理しないことを証明します。実装の検討で、Futureの1回のpollが長引くと
期限後の成功がタイマーより先に返る余地が見つかり、成功直前の再検査を追加しました。
回帰試験では10msの期限に対し30ms後に成功するFutureを使い、拒否を確認します。

別の状態遷移モデルでは、**開始数＝保持中＋解放済み＋引渡済み、開始数≤8、勝者≤1**を
任意の有限遷移列について証明しています。終了後は保留接続を残さず、再接続せず、
別候補の開始で元の時計や予算を変更しません。勝者のソケットは呼出側へ引き渡します。

実際のOSソケット解放、FutureのDrop、DNS候補の由来・重複排除、実行器の公平性と
モデルの全面的な対応は未証明です。poll自体が止まる環境で「実時間30秒以内に必ず返る」
とは言っていません。資源解放と通信はRustの回帰試験でも確認します。

## 管理者切替：復旧の手段を、確定前に消さない

旧サーバーを止める前に、別プロセスの自動切り戻しを準備します。
新サーバーが動いても、期限・検査・同じ起動の確認が揃うまでは確定できません。
確定記録を永続化してから自動切り戻しを解除します。

`CutoverProofs.cannot_stop_without_guard` は、復旧ガードがないと停止を許さないこと、
`deadline_and_boot_required` は、同じboot・時計逆行なし・開始から15分未満であることを
Rustの判断から証明します。ちょうど15分も拒否です。
`disarm_requires_same_durable_epoch` は、別の切替の古い確定記録で解除できないことを示します。
これらを実行できる読取専用CLIと、その厳格な入出力試験も追加しました。
[管理者プロトコル](cutover-policy.md)に呼出順序と前提をまとめています。

プロセス障害の状態モデルでは、旧サービスが止まり未確定なら復旧ガードが残り、
遅れて動いた自動watchdogも確定を取り消さないと証明しました。
ただし「記録の原子的永続化」「独立したwatchdog」は前提です。
このプロセス障害モデルだけではマシン再起動や途中書込みを扱えないため、次節の独立した復旧判断と保存モデルで補います。Python・systemdとモデルの全対応はP0の残課題です。公開更新の受領票も別項目として残ります。

この証明追加だけでは、既存の本番バイナリやroot所有の管理者プログラムは更新されません。
新しい判定を使うには、対応するバイナリと管理者アダプターを一緒に検証・配備する必要があります。


## 再起動・部分書込み：確定の途中を「確定済み」と見なさない

復旧タイマーは、マシンの再起動で失われることがあります。さらに、起動設定の変更中に
電源が落ちると、旧サーバーと新サーバーの両方に「起動する」印が残る場合があります。
そこで、起動するサービスを、別に永続化した復旧計画と確定記録から一つだけ選びます。

新サービスを選べるのは、計画・記録が有効で、同じ切替の確定であり、新候補の検査にも
通った場合だけです。記録が欠ける、途中までしかない、チェックサムが違う、古い切替の
ものだった場合は、検証済みの旧構成を選びます。旧構成も検証できなければ起動を止めます。
`RecoveryProofs.new_requires_bound_commit` と `torn_record_uses_old` がこのRust判断を証明します。

一時ファイルの名前は毎回新しく作り、途中のファイルは復旧候補にしません。
状態モデルでは「書きかけ→ファイル同期→名前変更→ディレクトリ同期」を区別し、
一時ファイルを同期しただけでは確定に昇格しないことを証明しました。名前変更後・
ディレクトリ同期前の中断では旧か新のどちらかになり得る前提を明示しています。
実際の試験では、これらの途中で書込みプロセスを強制終了して確認します。

起動許可にはboot IDと復旧計画の識別子を付けます。同じ許可で旧新の両方を起動できず、
再起動前の試運転許可も使い回せないことを証明しました。実systemdの依存・競合制御と
OSの書込みは証明の外側なので、ネットワークを持たない使い捨てVMで別途検証します。
新サービスの起動失敗からの切り戻しにも、実際の失敗・同じ起動許可・旧構成の再検証を要求します。

[復旧設計と試験境界](boot-recovery.md)に詳細があります。独立計画自体の媒体全損、rootによる改ざん、
OS永続化の正当性、Python/systemd全体とモデルの対応は保証していません。

## 復旧ガード自身の更新：途中から再開しても世代を巻き戻さない

既に変更先へ切り替わっていれば、再試行は読込み確認と完了記録だけを行います。
20件を追加し、そのうち8件は永続一式・原子的参照切替を前提にした状態モデルです。
任意の有限個の中断・再試行を含むモデルの遷移で、世代が減らず公開状態が変わらないことを示します。
ここで世代を数えるのは、保存を確認した境界です。参照先の名前変更後・ディレクトリ同期前に
電源が切れると旧か新のどちらも復旧結果になり得ます。その両方が完全な一式を参照する性質も、
追加公理に依存しない構成的な証明で確認しました。同期前の見かけの世代が戻らないとは主張しません。

## 公開更新の成功通知を、別の更新と取り違えない
